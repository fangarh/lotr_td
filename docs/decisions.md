# Decisions

Use this file as the project source of truth for accepted decisions.

## 2026-05-03

- Two-map Godot desktop MVP corridor is accepted as the next product direction. The target is an actual playable loop rather than another isolated spike: two authored scenario-driven maps, build spots instead of free placement, four tower roles (Eye direct damage, Forge area damage, Morgul control, Orc Camp blocker), four enemy roles (Gondor baseline, Rohirrim fast, Dwarven armored, Elven elite/control-resistant), economy with starting gold/costs/kill rewards, one upgrade level per tower, HUD-driven wave/restart flow, and win/loss without debug-key dependency. Android/touch-first UX, free placement, upgrade branches, final animations/VFX, path rerouting, full campaign progression, DLC/monetization, and complex enemy abilities are out of MVP scope. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-two-map-mvp-corridor-design.md`.
- Blocker-contact readability capture is accepted as capture-only Godot instrumentation. `tests/capture_blocker_contact_preview.gd` may instantiate `Main`, wait for the existing tower-owned `orc-blockade` runtime blocker, place an already-spawned enemy at the blocker position, verify `current_blocker_id()`, verify the existing signal bridge affects blocker HP, add capture-only `BlockerContactReviewMarker` helpers, and save `builds/previews/blocker_contact_preview.png`. This does not add production blocker visuals, enemy attack animations, final VFX, path rerouting, stacking policy, queueing, rewards, score, gold, wave/game-state ownership, tower retargeting, balance, upgrades, costs, or production placement UI. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-blocker-contact-readability-capture-design.md`.
- Temporary blocker HP contract is accepted as the next design boundary after slow zones. The first implementation should add runtime blocker HP/lifetime lifecycle ownership inside `SpikeObstacleTowerAdapter`, with read-only blocker output and explicit damage/removal APIs, before adding enemy movement blocking, enemy blocker attacks, path rerouting, stacking policy, tower retargeting, rewards, production placement UI, balance, or final spawned blocker visuals. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-temporary-blocker-hp-contract-design.md`.
- Temporary blocker HP lifecycle implementation: `SpikeObstacleTowerAdapter` now owns runtime temporary blockers spawned from `effect: "temporary-blocker"` catalog data, exposes `get_blocker_count()`, `get_blockers()`, and `apply_blocker_damage(blocker_id, amount)`, tracks id/source tower/position/radius/max/current HP/optional lifetime, and removes blockers through lethal damage or expiry. `shadow-tower-b3` references the test-scope `orc-blockade` effect in `spike_scenario.json`. This still does not add enemy movement blocking, enemy blocker attacks, path rerouting, stacking policy, tower retargeting, rewards, wave/game-state ownership, production placement UI, balance, or final spawned blocker visuals.
- First enemy/blocker interaction implementation: `Main` now synchronizes `SpikeObstacleTowerAdapter.get_blockers()` output into spawned `PlaceholderEnemy` proxies, and enemies stop while touching a blocker radius, emit `blocker_attack_requested(blocker_id, amount)`, and let `Main` bridge that signal back into `SpikeObstacleTowerAdapter.apply_blocker_damage()`. This is contact stop plus signal-bridged HP damage only; it does not add path rerouting, stacking policy, attack animations, final VFX, spawned blocker visuals, rewards, score, gold, wave/game-state ownership, tower retargeting, balance, upgrades, costs, or production placement UI. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-enemy-blocker-contact-design.md`.
- Timed slow-zone readability capture is accepted as capture-only Godot instrumentation. `tests/capture_timed_slow_zone_preview.gd` may instantiate `Main`, wait for a tower-owned timed slow zone, place an already-spawned enemy into that zone, verify `current_slow_multiplier() < 1.0`, add capture-only `TimedSlowZoneReviewMarker` helpers, and save `builds/previews/timed_slow_zone_preview.png`. This does not add blocker HP, path rerouting, stacking policy, enemy blocker attacks, production placement UI, rewards, damage, balance changes, or production spawned obstacle props. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-timed-slow-zone-readability-capture-design.md`.
- Live slow-zone propagation is accepted as the next narrow Godot obstacle slice. `Main` may synchronize the current `SpikeObstacleTowerAdapter.get_slow_zones()` output into already-spawned enemies so timed tower-owned zones affect active movement. This does not add blocker HP, path blocking/rerouting, stacking policy, enemy blocker attacks, production placement UI, visual spawned props, rewards, damage, or balance changes. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-live-slow-zone-propagation-design.md`.
- Live slow-zone propagation implementation: `Main` now pushes the current adapter slow-zone list into spawned enemy proxies after `SpikeObstacleTowerAdapter.advance(delta)` and when a new enemy is created. This makes timed tower-owned slow zones visible to active enemies while preserving `SpikeObstacleTowerAdapter` as data owner and `PlaceholderEnemy` as movement slow applier.
- Timed slow-zone spawning is the accepted first tower-owned obstacle behavior. One existing Godot spike tower candidate may declare an obstacle effect id and spawn temporary runtime slow zones through `SpikeObstacleTowerAdapter` on a timer. This keeps `SpikeTowerAttackAdapter` as damage/cooldown owner and does not add blocker HP, path blocking/rerouting, stacking rules, enemy blocker attacks, visual spawned props, production placement UI, rewards, damage, or balance changes. The design is recorded in `docs/superpowers/specs/2026-05-03-godot-timed-slow-zone-spawning-design.md`.
- Timed slow-zone spawning implementation: `shadow-tower-b2` now declares `obstacleEffectId: "corrupted-roots"`, spawn interval, lifetime, and spawn range in `spike_scenario.json`. `Main` registers tower proxies with `SpikeObstacleTowerAdapter`, passes path points into it, and advances it each frame. The adapter creates temporary runtime slow-zone dictionaries at nearby path points and expires them by lifetime; existing spawned enemies are not dynamically re-bound to newly spawned zones in this slice.
- Godot obstacle tower ownership direction: before adding blocker HP, stacking rules, path rerouting, enemy blocker attacks, obstacle lifetimes, or production placement UI, introduce a narrow scene-level `SpikeObstacleTowerAdapter`. The adapter owns registration of runtime obstacle effects from existing JSON obstacle placements and exposes read-only slow-zone data to spawned enemies. `Main` remains the composition root, `PlaceholderObstacle` remains visual-only, `PlaceholderEnemy` still applies movement slow locally, and `SpikeTowerAttackAdapter` keeps enemy damage/cooldown ownership. The accepted design is recorded in `docs/superpowers/specs/2026-05-03-godot-obstacle-tower-ownership-design.md`.
- Godot obstacle tower ownership implementation: `SpikeObstacleTowerAdapter` is now a scene-level adapter in `scenes/main.tscn`. It registers existing static obstacle placements as runtime obstacle effects, exposes `get_slow_zones()`, and owns slow-zone effect collection that previously lived in `Main`. This preserves the slow-only gameplay contract and still does not add blocker HP, path blocking/rerouting, stacking rules, obstacle lifetime, tower cooldown spawning, enemy blocker attacks, production placement UI, rewards, damage, or balance changes.
- Godot slow-zone readability capture: `tests/capture_spike_slow_zone_preview.gd` is local visual instrumentation for the first obstacle slow-zone contract. It validates an active enemy slow multiplier before saving `builds/previews/spike_slow_zone_preview.png` and adds capture-only `SlowZoneReviewMarker` / label helpers for review. This does not add production UI, obstacle placement UI, path blocking, rerouting, blocker HP, enemy blocker attacks, stacking rules, combat ownership, wave-state ownership, or balance changes.
- First Godot obstacle gameplay contract: corrupted-roots obstacle placements may now declare `effect: "slow-zone"` with `slowMultiplier` and `radius` in JSON. `Main` translates placed obstacles into world-space slow-zone dictionaries and passes them to spawned `PlaceholderEnemy` proxies; enemy movement applies the strongest active multiplier while inside a zone. This is intentionally a slow-only spike: no path blocking, rerouting, blocker HP, enemy blocker attacks, stacking design, production placement UI, rewards, damage, wave scheduling, restart flow, or balance pass.
- Terminal HUD action visual lock: the Godot spike now has a dedicated terminal action capture contract at `tests/capture_spike_hud_action_states.gd`. It prepares `wave_clear`, `basic_win`, and `basic_loss` through existing `Main`/adapter hooks, verifies the compact HUD action text before capture, and saves desktop plus rotated-phone landscape PNGs for each state. This is visual/test instrumentation only; it does not change gameplay ownership, balance, auto-advance, restart screens, pathing, rewards, or damage.
- First Godot terminal HUD action shell: `SpikeHud` may show one compact `ActionButton` inside the top HUD bar. It stays hidden while a wave is `running`, emits `next_wave_requested` from `wave_clear`, and emits `restart_requested` from `basic_win` / `basic_loss`. `Main` remains the composition root that calls `start_next_wave_manually()` and `restart_current_scenario_manually()`; HUD does not own wave scheduling, restart state, path breaches, rewards, damage, balance, or production menu flow.
- Debug manual restart key: the Godot spike may use `R` as a temporary debug-only input hook for `Main.restart_current_scenario_manually()`. The key is intentionally limited to local review and inherits the restart method's terminal-only `basic_win` / `basic_loss` guard. It does not add a HUD button, production restart screen, automatic retry, balance changes, or new ownership in game-state, combat, wave-state, or tower attack adapters.
- Manual Godot scenario restart boundary: `Main.restart_current_scenario_manually()` is a narrow local-review hook allowed only from terminal `basic_win` or `basic_loss`. It rebuilds the current JSON-backed spike runtime through the composition root, resets combat kill/reward/tracked state and tower attack runtime state, then starts the first wave again. It is not UI, not automatic retry, not a production restart screen, and it does not move wave scheduling, damage, rewards, path breaches, or tower cooldown ownership into `SpikeGameStateAdapter`.
- Godot mobile HUD visual verification must use a rotated phone landscape viewport for the current spike capture. `tests/capture_spike_hud_mobile_preview.gd` now captures `844x390` and saves `spike_hud_mobile_landscape_preview.png`; portrait `390x844` is not accepted as the primary rotated-phone HUD preview for this step.

## 2026-05-02

- First Godot HUD option implemented: `SpikeHud` now uses the recommended read-only mobile-safe top bar rather than the earlier debug panel. The bar shows state, wave, lives, breaches, and active enemies, wraps to two rows on narrow mobile widths, and intentionally has no `Next wave` button or gameplay ownership.
- HUD direction exploration is captured as a browser-viewable mockup at `docs/mockups/hud-options.html`. The three compared options are: read-only mobile-safe HUD bar, debug panel plus `Next wave`, and a fuller production HUD shell. No implementation decision beyond visual comparison is locked by the mockup; the current recommendation remains the read-only mobile-safe bar as the smallest next Godot step.
- Tower attack readability tuning is complete as a visual-only spike adjustment. `SpikeTowerAttackAdapter` now adds a temporary ember `ProjectileReadabilityGlow` and `ProjectileReadabilityTrail` under each `ProjectileVisual`, slightly increases the B4 projectile preview model scale, and keeps the helper lifetime tied to the existing projectile visual. This does not change target selection, damage timing, cooldowns, kills, rewards, projectile collision, wave state, or balance.
- Tower attack capture-only pass is complete as local visual instrumentation: `tests/capture_tower_attack_readability_preview.gd` saves `builds/previews/tower_attack_readability_preview.png` and asserts that both `TowerFireCue` and `ProjectileVisual` exist in the captured frame. The capture showed that the current projectile is present but not very readable in the full-board view, so any adjustment remains a separate visual-only tuning pass with no gameplay ownership changes.
- Tower attack readability review will be split into a capture-only pass and an optional tuning pass. The capture-only pass must not change damage timing, target selection, projectile behavior, balance, or VFX parameters; any readability tuning happens only after inspecting the captured PNG.
- Godot multi-breach scenario progression is now locked by smoke coverage rather than new production ownership. `tests/smoke_scenario_progression.gd` drives the two-wave fixture through breach wave 1, manual next-wave start, breach wave 2, and terminal `basic_loss`, verifying no kills/rewards and HUD refresh. The existing contracts remain unchanged: no auto next-wave, no production loss screen, no balance pass, and no pathing rewrite.
- Godot HUD readability capture: the debug HUD keeps a small top-left translucent dark `DebugPanel` behind its text and has a dedicated capture script at `tests/capture_spike_hud_preview.gd`, saving `builds/previews/spike_hud_preview.png` for local visual review. This remains local instrumentation, not production HUD styling, layout, input, or mobile UI.
- First Godot debug HUD boundary: `scripts/spike_hud.gd` is a read-only `Control` adapter for the spike scene. It displays `SpikeGameStateAdapter`, `SpikeWaveStateAdapter`, and `SpikeCombatAdapter` state as a compact debug readout, while `Main` only binds existing adapters and refreshes it. The HUD does not own gameplay state, buttons, next-wave progression, path breaches, rewards, tower cooldowns, balance, or production UI flow.
- Godot scenario-configured base lives: the spike JSON now owns `gameState.baseLives` as portable scenario data, and `Main` passes it into `SpikeGameStateAdapter.configure_base_lives()` before the first wave starts. Missing or invalid values still fall back to at least 1 life. This does not add UI/HUD, balance tuning, pathing changes, automatic next-wave behavior, or production loss screens.
- Context reset handoff policy: after a context cleanup, the resume prompt should stay short and should point the next session to `AGENTS.md`, required Obsidian source-of-truth notes, the Godot root, verification rules, the last completed step, and the recommended next step. Do not duplicate the whole project state in the prompt; detailed contracts and history should be recovered from `docs/` and the codebase unless there is a very recent unstabilized detail that is not yet documented.
- Godot enemy endpoint breach wiring: `PlaceholderEnemy` now emits `path_breached(enemy)` once when it reaches the final configured path point, hides/stops itself, and leaves the live targeting pool. `Main` handles that signal by calling `SpikeGameStateAdapter.mark_path_breach()`, unregistering the enemy through `SpikeCombatAdapter.unregister_enemy()`, and queueing the proxy for removal so `SpikeWaveStateAdapter` sees the normal `enemy_removed` path. Endpoint breaches do not count as kills, do not grant rewards, do not add combat damage, and do not rewrite pathing or introduce production loss UI.
- First Godot path-breach/loss boundary: `SpikeGameStateAdapter` now owns only explicit breach accounting above wave-state. It exposes configured base lives, breach count, `mark_path_breach()`, `basic_loss`, and loss completion state. Breach events are accepted only while a wave is `running`; this does not add enemy endpoint detection, base damage from `PlaceholderEnemy`, UI, automatic wave scheduling, combat rewards, tower cooldown ownership, or balance rules.
- Debug next-wave key: the Godot spike may use `N` as a temporary debug-only input hook for `Main.start_next_wave_manually()`. The key is intentionally a composition-root convenience for local review: it does not create production HUD/UI, automatic next-wave scheduling, path breach/loss handling, rewards, damage, tower cooldown ownership, or balance behavior.
- Manual Godot next-wave hook: `Main.start_next_wave_manually()` is the first explicit composition-root bridge from `SpikeGameStateAdapter.wave_clear` to the next `WaveRunner` wave. It only runs from `wave_clear`, starts the next `WaveRunner` wave, starts `SpikeWaveStateAdapter` for the new active wave id, emits immediate zero-delay spawns, and returns `false` while a wave is still running or after `basic_win`. This is not UI, not automatic next-wave scheduling, and it does not move damage, rewards, tower cooldowns, path breaches, loss state, or balance into game-state.
- First Godot game state adapter: `scripts/spike_game_state_adapter.gd` is a scene-level owner for minimal scenario progression state above wave-state. It tracks configured wave ids, the current wave index, and `idle` / `running` / `wave_clear` / `basic_win` states through manual `start_first_wave`, `start_next_wave`, and `mark_wave_clear` hooks. `Main` wires it to first-wave start and `SpikeWaveStateAdapter.wave_cleared`, but it does not own `WaveRunner` scheduling, damage, rewards, tower cooldowns, path breaches, UI, loss state, or automatic next-wave start.
- Tower targeting readability pass: `SpikeTowerAttackAdapter` keeps its nearest-live-target behavior explicit by ignoring invalid or non-living tracked targets from `SpikeCombatAdapter.get_tracked_enemies()`. Each tower fire now also spawns a short visual-only `TowerFireCue` near the firing tower, including towers without a projectile model. The cue expires through adapter advancement and does not affect target selection, damage timing, kills, rewards, wave state, or projectile physics.
- B4 projectile movement preview: `SpikeTowerAttackAdapter` now treats the B4 shot as visual-only moving state with start/end positions, progress, and lifetime. The visual starts near the firing tower, moves toward the targeted enemy during adapter advancement, and expires after `projectile_visual_lifetime`; damage, kills, and rewards still happen immediately through `SpikeCombatAdapter.apply_damage(enemy, amount)`, not through projectile collision, hit timing, or physics.
- First Godot wave state adapter: `scripts/spike_wave_state_adapter.gd` is a scene-level owner for minimal wave-clear state. It tracks the active wave id, expected spawn count, spawned enemies, active enemies, removed enemies, and a spawning-complete flag, listening to `SpikeCombatAdapter.enemy_removed` rather than owning enemy damage/removal. `WaveRunner` remains only the spawn scheduler, `SpikeCombatAdapter` remains combat/death/reward owner, and no UI, path breach, next-wave automation, balance, or win/loss logic is included in this slice.
- First Godot tower attack adapter: `scripts/spike_tower_attack_adapter.gd` is a scene-level `Node3D` owner between placed tower proxies and `SpikeCombatAdapter`. It registers placed tower nodes with catalog `range`, `damage`, `fireRate`, and optional `projectileModelPath`, targets enemies through a read-only `SpikeCombatAdapter.get_tracked_enemies()` view, and applies damage only through `combat_adapter.apply_damage(enemy, amount)`. `PlaceholderTower` remains a visual proxy, `SpikeCombatAdapter` still owns damage/death/removal/rewards, and `WaveRunner` scheduling is unchanged. B4 projectile output is limited to a short visual-only review instance, not production projectile movement or hit physics.

No tower targeting, projectile movement, damage, enemy pathing, costs, upgrades, or combat ownership changes are included in this pass.

- First Godot enemy lifecycle adapter: `PlaceholderEnemy` now reads catalog health, tracks `max_health` and `current_health`, exposes `apply_damage(amount)`, `is_alive()`, and `get_health_fraction()`, emits `health_changed` and `died`, stops processing and hides itself on death, and adds a simple 3D health bar. This is a local scene adapter only; wave completion, rewards, tower targeting, and removal ownership are still not implemented in Godot.
- Downloadable content and monetization direction: support downloadable content packs through manifests, a content registry, entitlement checks, installers, and storefront-specific delivery providers. Paid gameplay DLC must be isolated from the base campaign balance; visual monetization is cosmetic only. Free and seasonal packs are allowed, and claimed event content remains owned forever.
- DLC architecture policy: use inheritance for gameplay/presentation behavior contracts, not for ownership or delivery. Avoid content-specific `if/case` branches by registering content through manifests and ids; downloaded DLC should initially be asset/data-only and select built-in behaviors rather than shipping arbitrary new scripts.
- Godot export outputs stay under `shadow-conquest/builds/`, and that directory has a `.gdignore` marker so exported Web/Windows artifacts are not re-imported as project resources.
- Asset licensing: Tripo3D free-plan outputs must not be assumed commercially usable; any shipped AI-generated model needs tracked license/plan evidence.
- Current browser/Canvas build remains a prototype/reference for rules, balance, data shape, map scale, UI intent, and Shadow faction framing rather than the final runtime direction.
- Game view in the current browser prototype remains desktop-only. Mobile web layout is intentionally out of scope.
- Base logical tile size: `200x200`, projected as an isometric diamond `400x200` before `viewScale`.
- Camera: the canvas supports drag panning and wheel panning. Large maps are expected and should not be forced to fit fully on screen.
- Campaign map sizes: levels grow from `32x32` to `50x50`.
- Rendering optimization: map drawing should use visible tile bounds instead of always drawing every tile.
- Current game identity is pivoting from heroic defense to Shadow conquest.
- Future enemies should be Elves, Men, Dwarves, and allied Free Peoples rather than Orcs and Mordor forces.
- Tower attacks are not final. Do not lock balance until the new dark tower families are discussed.
- At least one or two tower families should create obstacles on the enemy path.
- Candidate obstacle towers:
  - Orc shield line / soldier blockade: temporary units standing on the path.
  - Spider webs / corrupted roots: soft control zones that slow or bind attackers.
- Android portability matters, but the accepted direction is now Godot/GDScript rather than a Kotlin port. Keep domain logic and data separable from renderer/UI details so the existing prototype can be migrated cleanly.
- Obsidian documentation is live project memory. Every project change, including small refactors and pauses, must update or explicitly re-check the relevant `docs/` notes before the work is claimed complete.
- Current architecture boundaries:
  - `src/camera.js` owns portable projection, scale, visible bounds, picking, and camera clamping.
  - `src/renderer.js` owns Canvas 2D scene drawing and draw-layer order.
  - `src/ui.js` owns DOM rendering for HUD, level selection, tower buttons, selection actions, tester HUD, status, and sound-toggle state.
  - `src/storage.js` owns browser persistence for campaign progress and sound preference.
  - `src/audio.js` owns WebAudio context creation and sound playback.
  - `src/input.js` owns browser event wiring for controls and canvas input.
  - `src/simulation.js` owns spawning timers, enemy creation, enemy movement, target selection helpers, tower placement, tower upgrades, tower selling/refund value, tower cooldown/attack orchestration, damage application with hit/slow/splash handling, projectile/beam/mark/shockwave effect creation, kill rewards/effects, outcome transitions, projectile aging, and effect aging.
  - `src/main.js` remains the browser composition root plus game state, game loop wiring, browser-side status/sound/save callbacks, and callbacks between modules.
