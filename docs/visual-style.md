# Visual Style

## Camera And Tile Scale

- Godot production target: mobile application first, with desktop browser and Windows executable secondary.
- Current browser prototype remains desktop-only and should not add a mobile web layout.
- Godot production view is 2.5D: a 3D scene with a fixed orthographic isometric camera, not free-camera full 3D.
- Logical tile: `200x200`.
- Isometric diamond before scaling: `400x200`.
- Large maps are expected; camera movement is the way to inspect them.
- Do not shrink the whole map to fit the viewport as the main experience.
- Allow pan and zoom. Avoid free camera rotation in the first production slice.

## Terrain

Terrain should feel like a continuous surface made of large isometric cells:
- homogeneous but not identical;
- soft seeded variation per tile;
- thin grid lines;
- roads as surfaces, not flat board-game strips;
- later: corruption and terrain blending.
- built in Godot as simple 3D ground/tile geometry on the XZ plane.

Trees are currently allowed to stay as simple triangles until terrain is settled.

## Tower Shape Guidance

Avoid silhouettes that read as rockets, missiles, or sci-fi structures.

Preferred tower traits:
- squat and heavy;
- clear base inside the tile;
- strong material identity;
- readable from zoomed-out mobile and desktop views;
- 3D through simple planes, light, and shadow rather than excessive spikes.

Dark tower materials:
- black basalt;
- iron;
- bone;
- red ember light;
- sickly Morgul green;
- ash, smoke, cracked stone;
- rough timber and spikes for Orc structures.

## Current Visual Caveats

- Existing Gondor tower visuals are temporary and likely to be replaced by Shadow tower families.
- The first Godot spike now uses catalog-driven tower asset paths. `res://assets/models/towers/base.glb` remains the base Eye tower proxy; `shadow_tower_b2.glb`, textured `shadow_tower_b3_textured/base.obj`, and `shadow_tower_b4.glb` are placed as additional Shadow tower visual proxies. All use the shared `PlaceholderTower` auto-fit, slight isometric yaw, dark base marker, and red ember beacon/light. The B3 proxy uses explicit diffuse, normal, metallic, and roughness texture maps from `b3.zip`. The B4 proxy has a static visual-only projectile preview from `shoot.zip` via `shadow_tower_b4_shot.glb`, and the tower attack adapter may spawn the same model as a short visual-only moving shot review node from tower to target; it is not final projectile art, collision, hit timing, or hit feedback.
- Tower shots now include a very short red-orange `TowerFireCue` near the firing tower. This is a temporary readability marker for the spike scene, not final VFX, muzzle logic, lighting design, or hit feedback. `ProjectileVisual` now also includes temporary ember `ProjectileReadabilityGlow` and `ProjectileReadabilityTrail` children so the B4 shot reads in the full-board capture; these are spike readability helpers, not final projectile art or hit feedback. `tests/capture_tower_attack_readability_preview.gd` saves `builds/previews/tower_attack_readability_preview.png` for local review.
- The path now supports a catalog-driven visual road surface model from `land.zip` as `res://assets/models/terrain/ash_road_surface.glb`. `BoardView` places it over primitive path tiles for asset review while the underlying tile path, movement points, and pathing rules remain unchanged.
- The first obstacle proxy is a Godot-native corrupted roots/web visual: dark ground patch, low root shapes, thin sickly green web strands, and a subtle Morgul glow. It should read as future path-control without implying permanent path rerouting yet.
- Temporary blocker HP and enemy contact are implemented as mechanics/data contracts, not as accepted production visuals. The current `orc-blockade` fixture can stop an enemy and take signal-bridged damage in smoke coverage. `tests/capture_blocker_contact_preview.gd` now provides a local PNG review path with capture-only `BlockerContactReviewMarker` helpers, saving `builds/previews/blocker_contact_preview.png`. It still has no production spawned blocker prop, attack animation, final VFX, or accepted production contact marker.
- The first slow-zone review capture is `builds/previews/spike_slow_zone_preview.png`, generated by `tests/capture_spike_slow_zone_preview.gd`. It uses capture-only `SlowZoneReviewMarker` and label helpers to make the slow effect readable in PNG review; these helpers are not production UI, obstacle art, pathing indicators, or final VFX.
- The timed tower-owned slow-zone review capture is `builds/previews/timed_slow_zone_preview.png`, generated by `tests/capture_timed_slow_zone_preview.gd`. It uses capture-only `TimedSlowZoneReviewMarker` and label helpers after verifying an already-spawned enemy is slowed by the temporary zone; these helpers are not production spawned obstacle props, pathing indicators, or final VFX.
- The first imported terrain prop candidate is a procedural Mordor rock cluster GLB: low ash patch, jagged black basalt shards, subtle ember cracks, and small Morgul-green lichen accents. It is decorative only and should stay lower and quieter than towers/enemies so it supports terrain corruption without reading as an obstacle or target.
- The first enemy proxy iteration is a Godot-native primitive Gondor soldier: simple blue-grey body, skin-tone head, light metal helmet, white/blue shield, spear, and small banner. It is intentionally low-detail for mobile readability and remains a visual proxy until a cleaned GLB or animated character source is chosen.
- The Elven archer asset proxy has been replaced from the user-provided `elf.zip` using `base_basic_pbr.glb`. It is still wired as `res://assets/models/enemies/elf_archer_proxy.glb` through the `elven-archer` catalog id, but the new import is a larger single-mesh GLB rather than the previous procedural multi-part proxy. It should be re-reviewed under the fixed isometric camera before treating its silhouette, materials, or scale as final.
- Current Elven archer spike fit still uses a larger-than-realistic proxy scale for readability from the full board camera: about `1.15` scene units tall inside a `0.86` footprint. This is acceptable for the prototype because enemy identity matters more than exact anatomical scale in the first mobile-readable pass.
- The bright green Elven archer base remains a temporary gameplay-readability marker and should be revisited when enemy selection/health UI exists.
- The second imported Free Peoples enemy asset candidate is now refreshed from the user-provided `gnome.zip` PBR export as `res://assets/models/enemies/dwarven_warrior_proxy.glb`, still wired as `dwarven-warrior` through the spike enemy catalog. Current fit uses about `0.98` scene units tall inside a `0.82` footprint with a muted stone base marker so it stays visibly shorter and heavier than the Elven archer while still reading from the full-board camera.
- The third imported Free Peoples enemy asset candidate is now refreshed from the user-provided `gondor.zip` PBR export as `res://assets/models/enemies/gondor_warrior_proxy.glb`, still wired as `gondor-warrior` through the spike enemy catalog. Current fit uses about `1.05` scene units tall inside a `0.84` footprint with a subdued blue-grey base marker, keeping it close to the Gondor soldier identity without replacing the primitive fallback.
- Enemy proxies now include simple 3D health bars above the model as the first gameplay-state readability layer. Keep these compact and high-contrast; they are temporary until a production mobile UI/readability pass decides final enemy markers, selection affordances, and health presentation.
- Imported enemy base markers should be treated as temporary readability aids, not final UI. Prefer subdued markers for new candidates unless a specific asset needs stronger contrast for review.
- The renderer boundary is now `src/renderer.js`; canvas draw layers, map traversal, towers, enemies, projectiles, effects, and hover rendering are no longer in `src/main.js`.
- Detailed tower art is still canvas-command based and includes temporary heroic silhouettes such as Gondor/Rohan/Elven/Dwarven motifs.
- Future rich tower visuals should move through the Godot asset/scene pipeline instead of adding more complex browser canvas-only art.
- Tripo3D-generated models are acceptable as rough sources if they are cleaned in Blender and imported as optimized GLB/glTF 2.0 assets.
- Keep mobile readability ahead of model detail. Favor strong silhouettes, simple materials, and controlled scale over dense geometry.
- Imported tower models should stay within roughly one tile footprint and remain readable under the fixed orthographic camera. Use local fit controls and small readability accents before changing the source model. Keep a primitive fallback until the asset source and export behavior are stable.
- Background landmarks should stay subtle. Avoid large isolated geometric blocks that look like artifacts.
- Prototype UI should remain dense, desktop-oriented, and functional. Godot mobile UI should be designed separately around touch targets and small-screen scanning.
- The first Godot `HUD` now extends the selected mobile-safe top bar direction from `docs/mockups/hud-options.html`: a dark translucent top bar with small high-contrast labels for state, wave, lives, breaches, and active enemies, plus one compact action button that appears only for valid terminal/progression states. It now also has a compact desktop build strip for current gold, build spot selection, tower type selection, and a Build button. The build controls are intentionally signal-only and desktop-first; they hide on narrow layouts rather than forcing touch UI into this MVP block. The top bar uses an intermediate-width breakpoint to avoid overlap between scenario selector, status fields, action button, and build controls. `tests/capture_spike_hud_preview.gd` saves the desktop running-state preview, and `tests/capture_spike_hud_mobile_preview.gd` uses a rotated-phone landscape viewport `844x390`, saving `builds/previews/spike_hud_mobile_landscape_preview.png`. `tests/capture_spike_hud_action_states.gd` saves explicit action-state previews for `wave_clear`, `basic_win`, and `basic_loss` in both desktop and rotated-phone landscape so `Next wave` and `Restart` can be reviewed in PNG form. Treat this as the first spike HUD action/build composition, not final typography, icons, touch controls, production shop UI, or production status messaging.
